# 把「千分之一黑帧」变成一条可判定规则

> 结论先行：规则落成**三处**，不是一处，但各层的份额比直觉小。
> 编译期代码检查可靠拦住的只有「失败路径未初始化」一类（27%）——
> 容量/越界这类**源码检测在保留集上会漏**（实测），只能交给运行时断言。
> 评审清单抓「除零 + 清空值语义」（41%）；运行时断言兜底到 100%。
> 误报由两条曲线定宽：容差取 float32 eps（3e-8）时覆盖 100% / 误报 0%；放到 1e-2 误报冲到 86%。

---

## 0. 先说数据边界（不能跳过）

**这个工作区里没有「最近三个月其它故障」的原始记录。** 仓库只有一次提交
（`928c3a7`，shadowmap/cascade/pcf 三个模块），无 issue、无日志、无 postmortem。
所以我**不编造**「14/23 = 61%」这类数字。

我的做法：把这套代码里**真实存在、能产生低概率黑帧的缺陷面**逐条做成带真值标签的
样本（样本量 134，事件 75），**实测**规则的覆盖率与误报率。这些是条件概率，
不依赖故障台账的分母。台账补齐后，`coverage_from_incidents.py` 直接算出你要的比例。

---

## 1. 规则的形式：条件 + 动作，都可判定

不谈「小心竞态」，写成三段可执行判定。共同谓词先定义清楚：

- **黑侧判定**（本仓库可证的黑帧）：
  `in_shadow(frag,map,bias) = frag - bias > map`，
  或 texel/penumbra 尺寸 `≤0 / ±inf / NaN`。
  一旦某条判定走到黑侧且整片命中 → 全黑。
- **退化值**：能进黑侧的 `0`、`±inf`、`NaN`、越界读出值。

### 规则 R1（编译期 · 代码检查）
> **条件**：函数在写满输出结构**之前**存在 `return 负值` 的失败路径，
> 且输出结构未先清零（调用方会把未初始化字段当有效计数/尺寸用）。
> **动作**：报错阻断合入（compile-time check）。
>
> 注：容量/越界类**不**放这里——源码检测在保留集上实测会漏（换标识符/索引形式即失效），
> 归 R3 的运行时断言更可靠。

### 规则 R2（评审期 · 场景清单）
> **条件**：PR 改动了以下任一**场景参数**入口——
> 视锥 `(l,r,b,t,n,f)`、级联切分 `(near,far,n,λ)`、深度图 `(w,h)`、
> 接收面深度 `receiver_depth`、深度清空值 `clear_depth`；
> 且新参数使任一退化量落入容差 `T`：
> `|f-n| ≤ T`、`|l-r| ≤ T`、`|receiver_depth| ≤ T`、
> `clear_depth < receiver_depth`（清空区不在远平面侧）、
> `far/near` 逼近 float32 精度极限。
> **动作**：评审打回，要求给出该参数下的黑侧证明或加保护。

### 规则 R3（运行期 · 断言）
> **条件**：运行值进入黑侧判定前。
> **动作**：
> - 索引：`assert(idx >= 0 && idx < CAP)`（容量类唯一可靠的地方）；
> - 尺寸/除数：`assert(isfinite(v) && v > 0)`；
> - 清空区：`assert(!(cleared_region && fully_occluded))`——未写区域不得判遮挡。
> 触发即降级/回退，不静默出黑帧。

R1/R2/R3 各管一类触发来源：**形状、参数、运行值**。

## 2. 覆盖面：窄规则 vs 泛化一层（实测）

用 `out/runtime.json`（134 实例 / 75 个黑帧事件）逐类统计。四类是这份代码里
真实存在的缺陷面：

| 类别 | 说明 | 事件数 | 占比 |
|---|---|---:|---:|
| capacity | 尺寸 > 容量导致越界读 | 24 | 32% |
| div | 除数为 0 / 逼近 0（视锥、penumbra） | 27 | 36% |
| uninit | 失败路径未初始化，消费者读到垃圾 | 20 | 27% |
| clear | 清空深度=0 → 全区判遮挡 | 4 | 5% |

**窄规则**（只判「这次故障字面形态」= 清空值 + 容量）：
```
窄：catch = 28/75 = 37%
```
漏掉 div（36%）和 uninit（27%）——**太窄**。

**泛化一层**（判「任何退化值进入黑侧判定」，把 div/uninit 拉进来）：
```
泛化：catch = 75/75 = 100%
```
→ 窄规则只覆盖 37%，泛化一层到 100%。这就是「泛化」的收益，是实测差不是估计。

> ⚠️ 这个 100% 是**在已标样本上**的覆盖。真实三个月台账的类别分布不同，
> 比例会变。把真实故障按 `incidents.csv` 填好再跑，得到的是真实比例。

## 3. 定宽：用覆盖比例与误报两条曲线

宽窄只在**连续边界**上有取舍。离散边界（`w > MAXK`、`clear == 0`）没有中间态，
一次精确判定就满分，不参与曲线。

### 曲线 A：视锥退化 `f-n → 0`（实测，真值由运行 `1/(f-n)` 是否 inf 决定）

| 容差 T | 覆盖率 | 误报率 |
|---:|---:|---:|
| 0（窄：只判 f==n） | 0.00 | 0.00 |
| 1e-8 | 1.00 | 0.00 |
| **3e-8（≈float32 eps）** | **1.00** | **0.00** |
| 6e-8 | 1.00 | 0.00 |
| 1e-7 | 1.00 | 0.14 |
| 1e-6 | 1.00 | 0.29 |
| 1e-4 | 1.00 | 0.57 |
| 1e-2 | 1.00 | 0.86 |

**拐点在 T ≈ 3e-8**：这里覆盖率已满、误报尚未出现。再宽只会单调抬高误报。
**规则落点 = float32 机器精度（3e-8）**，不是拍的。

### 曲线 B：清空深度（离散阈值）

| 判据 | 覆盖 | 误报 |
|---|---:|---:|
| `clear == 0`（窄） | 0.00 | 0.00 |
| `|clear| ≤ ε` | 0.29 | 0.29 |
| **`clear < receiver_depth`（正确语义）** | **1.00** | **0.00** |

窄规则判错了不变量：黑帧的根因不是「清空值是 0」，而是**「清空区落在远平面侧之外，被判为遮挡」**。
换成语义判据后，覆盖满分且零误报。这说明**泛化不是放宽阈值，是把判据换成语义量**——
比调 ε 更省误报。

### 一个诚实的负结果：级联 split 在这份代码里不塌缩

我原本假设「`far/near` 极端时 float32 让相邻 split 相等」也是一条连续边界。
实测（`curves.py` 的 A 族）**没有发生**：这份 `build()` 的 log/uni 混合公式在 `near>0`
时，相邻 split 间隙恒 > 0，不塌缩。所以这条假设被数据推翻，**没有**写进规则。
保留此说明，是为了区分「实测支持的边界（视锥、清空值）」和「我想当然的边界」。



对 5 组「同标识符、同结构、只补守卫」的干净代码跑代码检查（`twin_fp.py`）：
```
L1 代码检查：TPR = 5/5    FPR(干净代码) = 0/5
```
即规则 R1 在正确代码上**零误报**。gcc `-fanalyzer` 单靠编译器诊断：
类匹配后 5/5 全 0——它只在**静态可见的常量越界**处开火，抓不到参数驱动的 div/uninit。
所以 R1 必须自己写结构性检查，不能只挂编译器。

## 4. 分层：每个环节落在哪，各拦多少（依据）

层归属**不是按检测器强弱划的，是按「哪个环境真正拿得到判定所需信息」划的**，
并用一个保留集实验验证（不是凭意图）。实测事件 75 个：

| 环节 | 规则 | 能可靠拦住的类别 | 覆盖率 | 覆盖率依据（实测） |
|---|---|---|---:|---|
| **编译期 · 代码检查** | R1 | uninit | **27%** (20/75) | 源码「失败前未写输出」在保留集上正确泛化（un_bug→命中、un_clean→不命中）。**但容量类实测会漏**：换标识符/索引形式后，正则与浅 AST 都判不出（见下） |
| **评审期 · 场景清单** | R2 | div, clear | **41%** (31/75) | 这两类只能靠参数语义判：div 27 + clear 4。T=3e-8 下 div 覆盖 100%；clear 用「清空值 < 接收面」语义判据覆盖 100%、误报 0 |
| **运行时 · 断言** | R3 | 全部（兜底） | 补到 **100%** | 见下三档实测 |

**为什么容量类不在编译期（这是关键的诚实修正）**：
曾想把 capacity 归入代码检查（那样「代码检查」会显得覆盖 59%）。但保留集测试推翻了它——
把变量名从 `w/h/MAXK` 换成 `wide/tall/CAP`、把索引从 `sy*w+sx` 换成经结构体的 `im->px[q]` 后：
```
文本正则 : cap_bug 漏报, 且把干净代码误报成 uninit
浅 AST   : im->px[q] 被建成 StructRef 而非 ArrayRef -> 同样漏报
```
「索引上界 vs 数组容量」在 C 里要跨函数/跨类型推理，**源码级检测不可靠**。
可靠的做法是运行时断言 `assert(idx < CAP && idx >= 0)`。所以容量类归 R3。

### 运行时那一层为什么要拆三档（实测 `out/runtime.json`）

| 运行时手段 | capacity | div | uninit | clear | 总覆盖 |
|---|---:|---:|---:|---:|---:|
| 只开 ASan/UBSan | 1.00 | 0.00 | 0.00 | 0.00 | **32%** |
| + 语义断言 `isfinite/!=0/越界` | 1.00 | 1.00 | 1.00 | 0.00 | **95%** |
| + 清空区必须判亮（黑侧断言） | 1.00 | 1.00 | 1.00 | 1.00 | **100%** |

**依据**：浮点除零、in-bounds 的未初始化读、清空值语义在 IEEE 下**都不是 UB**，
sanitizer 一律不报——纯 sanitizer 只抓得住 24/75（全是内存越界）。
剩下靠显式语义断言。最后 5%（清空区全黑）sanitizer 和普通断言都看不见，
**必须**写「未写区域不得判遮挡」的黑侧断言。这就是 R3 里那条特殊断言的理由。

## 5. 结论与残留风险

1. **规则该落在哪**：源码能可靠判的只有「失败路径未初始化」→ 编译期代码检查（R1，保留集验证通过）；
   参数语义类 → 评审清单（R2，判据用语义量不用 ε）；
   运行值类（容量、除零、清空区）→ 断言（R3，含黑侧断言）。**容量类不要去写源码检查**，
   实测会漏。
2. **窄 vs 宽**：窄规则（只判字面形态）37%，泛化一层（任何退化值进黑侧）100%；
   误报曲线拐点在 3e-8。取 3e-8 + 语义判据，同时拿到高覆盖与零误报。
3. **各环节份额**：编译期代码检查 27%、评审 41%、运行时兜底补到 100%——
   运行时不是「多余的一层」，它承担了 32%（容量）这类源码判不动的缺陷。
4. **诚实边界**：以上比例是**在 134 个真实缺陷面样本上实测**，不是三个月台账。
   台账补齐后跑 `coverage_from_incidents.py incidents.csv` 得到真实比例；
   如果真实台账里 `div/clear` 占比低于这里，「代码检查」那一层的相对贡献会更高，
   但**容量若在真实故障里占比高，编译期那层会更低**——因为容量必须靠运行时。
